I wanted to build something that looked closer to a real access control system than just another facial recognition demo.

Instead of simply comparing two images, I wanted a complete pipeline capable of enrolling people, recognizing faces in real time, storing embeddings inside Oracle Database, and exposing everything through a REST API.

---

Each stage has a specific responsibility. By separating them, I can improve or replace one component without rewriting the entire application.

---

## Registered Face

![Registered face](/articles/img/registered.png)

When a registered face appears, the system generates a new embedding and compares it against the vectors already stored in Oracle Database.

Instead of comparing images directly, only numerical vectors are compared, making recognition much faster and much more scalable.

---

## Unknown Face

![Unknown face](/articles/img/not-registered.png)

If no stored embedding is close enough to the captured one, the face is classified as unknown.

That decision isn't based on an exact match, but on the vector similarity returned by Oracle AI Vector Search.

---

## Why I Store Embeddings Instead of Images

One of the first design decisions I made was separating the original image from the recognition process.

Although I could store every captured image, recognition doesn't actually need them.

What the model really uses is the embedding generated by InsightFace.

---

## Separating Responsibilities

Instead of putting everything inside a single Python script, I split the project into different components.

```text
Desktop Application
        │
        ▼
     FastAPI
        │
        ▼
Oracle Database
        │
        ▼
 Streamlit Dashboard
```

Each service focuses on one responsibility.

The desktop application captures frames.

FastAPI exposes the API.

Oracle stores vectors and access logs.

Streamlit visualizes the collected data.

Keeping these responsibilities separated makes the project much easier to maintain.

---

## Why FastAPI

Recognition itself is only one part of the system.

I also wanted endpoints for enrolling new people, recognizing faces, querying logs, and generating analytics.

Using FastAPI made each feature available through independent REST endpoints.

```python
POST /enroll
POST /recognize
GET  /logs
POST /chat
```

The desktop application simply sends requests to the API instead of handling everything locally.

---

## Oracle as More Than Just a Database

Oracle isn't only storing information.

It also performs the similarity search between embeddings.

After generating a vector with InsightFace, the application sends it directly to Oracle, which returns the closest registered person using vector distance.

This avoids loading every embedding into Python just to compare them manually.

---

## AI-Powered Analytics

One feature I enjoyed building was the analytics endpoint.

Instead of writing SQL queries manually, I connected the access logs to an LLM through OpenRouter.

That allows questions such as:

```text
Who entered the building the most today?

Which employee had the earliest access?

Show all failed recognitions from yesterday.
```

The model generates SQL, queries Oracle, and returns the result in natural language.

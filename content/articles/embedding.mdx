If you've ever built a facial recognition system, you might think the hardest part is detecting a face. Surprisingly, that's usually not the case. The real challenge starts after the face has already been detected: **how do you recognize that same person later?**

A lot of people imagine that facial recognition systems simply store pictures and compare them every time someone appears in front of the camera. That would work... but it would also be slow and pretty unreliable. Instead, modern models like [InsightFace](https://github.com/deepinsight/insightface) convert each face into something called an **embedding**. It's basically a long list of numbers that mathematically represents that face. You can think of it as a digital fingerprint—not because it looks like one, but because it's unique enough to identify someone.

---

## Why Store Embeddings Instead of Images?

This is the question I asked myself while building my projects

Sure, I could save every captured image, but then I'd have to compare images every single time someone tried to access the system. That's expensive, slow and very sensitive to things like lighting, facial expressions or camera angles.

Embeddings solve that problem. Instead of comparing photos, I compare vectors. If two embeddings are very close mathematically, there's a good chance they belong to the same person.

Since those vectors need to be available every time the application starts, storing them in a database makes perfect sense.

In my case, I chose [Oracle Database](https://www.oracle.com/database/) because it has native support for vector operations. Alongside each embedding, I also store the original image as a BLOB, so I have both the mathematical representation and the original photo available whenever I need them.

## Saving the Embedding

Once InsightFace processes a detected face, it returns a floating-point vector. Oracle expects a vector format, so before saving it, I simply convert the NumPy array into something that can be inserted into the database.

```python
import array

vector_value = array.array("f", embedding.tolist())

cursor.execute(
    """
    INSERT INTO PERSON_FACES (person_id, embedding, face_image)
    VALUES (:person_id, :embedding, :face_image)
    """,
    {
        "person_id": person_id,
        "embedding": vector_value,
        "face_image": face_image_bytes,
    },
)
```

That's basically the entire process. Once it's stored, I never need to generate that embedding again unless I want to register a new photo for that person.

## Finding the Right Person

Now comes my favorite part.

Every time someone stands in front of the camera, the application generates a brand-new embedding. Instead of looping through every image I've stored, I simply ask Oracle to compare that new vector against all the vectors already in the database.

Oracle does the heavy lifting using the `VECTOR_DISTANCE` function.

```sql
SELECT
    p.id,
    p.name,
    MIN(VECTOR_DISTANCE(f.embedding, :embedding, COSINE)) AS distance
FROM PERSON_FACES f
JOIN DETECTED_PEOPLE p
ON p.id = f.person_id
GROUP BY p.id, p.name
ORDER BY distance
FETCH FIRST 1 ROW ONLY;
```

The cool part is that the database isn't comparing faces anymore. It's comparing numbers. It looks for the embedding that's mathematically closest to the new one and returns the best match.

That's why recognition stays fast even as more people are added to the system.

One thing I found really interesting while building this project is that the face image eventually becomes secondary. It's still useful for registration, auditing and visualization, but the actual recognition process almost never looks at the image again.

When I first started working with facial recognition, my first thought was simple: *why not just save every captured image and compare it later?* It sounds reasonable, but it's actually one of the slowest ways to recognize someone. Images are large, lighting changes all the time, faces rotate, expressions change, and comparing pixels simply doesn't scale very well.

Instead, I used [InsightFace](https://github.com/deepinsight/insightface) to convert every detected face into a **512-dimensional embedding**. Rather than storing visual information, I store a mathematical representation of the face. If two embeddings belong to the same person, they'll be very close in vector space. If they belong to different people, the distance between them becomes much larger. That's what the recognition process is really based on.

---

## Why Oracle VECTOR?

Since the application already produces embeddings, it made much more sense to store those vectors directly instead of trying to compare images myself. That's exactly where [Oracle AI Vector Search](https://www.oracle.com/database/ai-vector-search/) comes in.

Oracle provides a native `VECTOR` data type, so every embedding can be stored directly inside the database. Instead of saving hundreds of floating-point values across multiple columns or serializing them into text, I can insert the entire embedding as a single vector. That also means the database can perform similarity searches without requiring extra processing in the application.

The image above shows one of the vector records stored in the database. Even though it looks like a long list of numbers, this is actually the mathematical representation of a person's face. Every row stores a different embedding generated by the recognition model.

## Saving the Embedding

Once the face is detected, the embedding is returned as a NumPy array. Before sending it to Oracle, I convert it into a format that the Python Oracle driver accepts.

```python
import array

vector = array.array("f", embedding.tolist())

cursor.execute(
    """
    INSERT INTO PERSON_FACES (person_id, embedding)
    VALUES (:person_id, :embedding)
    """,
    {
        "person_id": person_id,
        "embedding": vector,
    },
)
```

From that point on, Oracle stores the entire embedding as a native vector. The application doesn't need to manually split the values or rebuild them later because the database already understands that they're part of a single vector.

---

## Finding the Closest Face

The interesting part happens during recognition. Every new face generates another embedding, and instead of downloading every stored vector and comparing them in Python, I let Oracle do the work.

Using the `VECTOR_DISTANCE()` function, the database calculates how close the new embedding is to every stored embedding and returns the closest match.

```sql
SELECT
    p.id,
    p.name,
    MIN(VECTOR_DISTANCE(f.embedding, :embedding, COSINE)) AS distance
FROM PERSON_FACES f
JOIN DETECTED_PEOPLE p
ON p.id = f.person_id
GROUP BY p.id, p.name
ORDER BY distance
FETCH FIRST 1 ROW ONLY;
```

This means the application only sends one embedding to the database, and Oracle handles the similarity search internally. The only thing the application receives back is the closest person and the calculated distance.

---

The recognition model only needs to generate an embedding, while Oracle is responsible for storing vectors and searching through them efficiently.

Instead of asking *"Which image looks the most similar?"*, the database asks *"Which vector is mathematically closest?"* That's exactly why modern facial recognition systems don't compare photos—they compare embeddings. Once those embeddings are stored as native Oracle vectors, recognition becomes nothing more than a fast vector similarity search.
